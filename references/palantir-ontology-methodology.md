# Palantir Ontology 进阶方法论参考

> 本文是「本体领航员」的进阶参考资料，供深度咨询时按需调用。核心规则已内置于 Agent MD 正文，本文补充细则与深度内容。

## 一、常见反模式清单（设计时必须规避）

1. **大爆炸式建模**：试图一次性建完全企业模型再上线。后果：上线周期被无限拉长，业务等不到价值。对策：先做试点场景。
2. **面向数据表而非面向决策**：从源系统的表结构反推对象，而不是从"要改进什么决策"出发。后果：本体沦为数据目录的翻版。
3. **对象粒度失当**：对象建得过粗（把"订单"和"合同"混为一谈）或过细（每个状态都单独立对象）。对策：以"业务团队口头会用到的名词"为粒度标尺。
4. **属性堆砌**：把源表所有字段都搬进对象属性，不做原始/派生区分。后果：本体臃肿、难以维护。
5. **只有读、没有写**：只建对象和链接，没有动作类型。后果：决策无法写回业务系统，闭环断裂，采纳率上不去。
6. **缺少 Owner 与治理**：概念定义无人负责，同名不同义、同义不同名蔓延。后果：本体逐渐失去可信度。
7. **把本体当一次性项目**：上线即收工，没有版本迭代和反馈闭环。
8. **忽略身份解析**：跨系统主键不一致时硬拼数据，产生"一个客户被拆成三个对象"的脏数据。
9. **权限后置**：动作类型没有在设计阶段就确定执行者和权限边界，上线后返工。
10. **忽视 AI grounding 价值**：只把本体当"更好的数据模型"，错过了让 AI Agent 落地业务操作的窗口。

## 二、Action Type 设计细则

动作类型是 Palantir 本体区别于普通知识图谱的关键——它把"决策"连接到"执行"。

设计每个动作需回答五问：
1. **谁来执行**（执行者角色，映射到权限体系）？
2. **前置校验规则**（可机判的条件，如"金额 ≤ 5 万""优先级 P1 且超 4 小时"）？
3. **写回目标**（精确到源系统的接口/表/流，而非"通知相关部门"这类模糊表述）？
4. **副作用与幂等性**（重复执行是否安全？是否需要事务/补偿）？
5. **审计要求**（执行留痕：谁、何时、依据什么规则、结果如何）？

设计要点：
- 动作命名用动词，如 `escalateTicket` / `approveClaim` / `createReplenishment`
- 一个动作只做一件事，复杂流程拆成多个动作 + 编排（不是塞进一个动作里）
- 校验规则尽量前移到动作层，减少业务系统侧重复逻辑

## 三、身份解析（Entity Resolution）策略

本体要求"同一业务实体在所有源系统中指向同一对象"，身份解析是打通的关键。

常见策略（按成熟度递增）：
1. **确定性匹配**：基于业务主键直接映射（如统一社会信用代码、设备序列号）。首选。
2. **规则匹配**：多字段组合规则（如"手机号 + 姓名拼音"）。
3. **模糊匹配/相似度**：用于非结构化或质量差的数据（如手工录入的客户名），需引入阈值与人工复核队列。
4. **主数据管理（MDM）**：对高频核心对象（客户、供应商）建 MDM 体系，本体消费 MDM 结果。

落地要点：
- 先对核心对象（通常 ≤ 10 类）做身份解析，不做全量
- 记录"疑似重复"清单交由人工 steward 仲裁，而非全自动合并
- 身份解析的规则要可解释、可回滚

## 四、AIP 与本体 grounding 架构

Palantir AIP（AI Platform）的核心设计：**把大模型 grounding 在本体之上，而非让模型直接读写原始数据**。

分层：
1. **对象层**：Agent 通过本体对象读取业务上下文（属性即上下文、链接即关系图谱）
2. **动作层**：Agent 通过动作类型执行受控操作，而非自由调用任意 API
3. **权限与审计**：Agent 的读/写权限继承本体对象与动作的权限体系，全程留痕

由此获得的收益：
- **消除幻觉**：模型回答引用的对象属性来自本体，而非凭空生成
- **可控可审计**：Agent 只能执行白名单动作，每次执行可追溯
- **业务可治理**：本体概念的变更由 steward 管理，AI 行为随之更新

## 五、采纳度量指标体系

衡量本体项目成功与否，建议建立如下度量看板：

| 维度 | 指标 | 说明 |
|------|------|------|
| 活跃度 | 周活跃用户数 / 月活 | 谁在用 |
| 覆盖度 | 决策覆盖率 | 目标场景中通过本体完成的决策占比 |
| 执行度 | 动作执行量 | 动作类型被触发次数（体现"写回"闭环） |
| AI 价值 | AI 调用量 | 本体被 AI/Agent 消费的频次 |
| 健康度 | 无引用对象/属性占比 | 越低越好，定期清理 |

采纳率不足的常见根因与对策：
- 根因：场景无业务 Owner → 对策：Owner 认领制 + 纳入团队复盘
- 根因：快赢未兑现 → 对策：收窄场景，先让一个决策真正变快
- 根因：IT 与业务割裂 → 对策：概念 steward 由业务 + IT 共担
